> 文档版本：V1.0  ·  确定日期：2026-10-10  ·  状态：**历史方案基线；当前实施状态以《MeterBill 成品实施记录》为准**

## 0. 项目定位与交付原则

**项目名称：** MeterBill（企业级多租户 AI API SaaS 计量计费与账务平台）。

**业务背景：** 一家向企业客户提供 AI 模型 API 的 SaaS 服务商，向不同租户销售套餐，根据模型、输入/输出 Token 等计量项和版本化价格规则计费，按月出账，经模拟支付渠道收款，并进行账务记载、退款、调整和对账。

**项目目标：** 构建可在 IDEA 本地开发、Docker Desktop 支撑基础设施、Apifox 验证 API、JMeter 验证性能、Linux 虚拟机完成部署和 CI/CD 的真实业务系统。采用工程化设计与证据驱动的验收方式，避免只有正常流程的 Demo。

**核心价值：** 技术能力围绕计量事件可靠接收、复杂计价、账单确定性、资金账务不变量、跨租户数据隔离、异步恢复、多实例安全和运维交付展开。所有关键功能要有运行结果、测试报告与故障演练证据。

**分工：** 用户通过 IntelliJ IDEA 编写代码、运行项目和测试；ChatGPT 分阶段提供设计、必要的完整代码、明确文件路径、操作步骤、Apifox 场景、数据库核对 SQL、JMeter 计划、问题排查、部署与验收。每轮可批量涉及多个文件。每个大模块完成后，必须完成规定的验收闭环，不能仅凭 HTTP 200 判定完成。

**实施约束：** 先保证业务正确性，再压测和优化；先解决当前真实问题，再引入中间件；优先复用成熟组件而非重复造轮子；在需要分布式设计的边界预留演进能力，但不提前承担微服务复杂度。

## 1. 范围与非目标

### 1.1 V1.0 必须实现的业务能力

1. 租户、用户、角色、API Key、租户间数据隔离；重要操作留审计记录。
2. 产品、模型、计量项、套餐、用量额度、阶梯价格和**不可变价格版本**。
3. 订阅创建、激活、到期、续订、取消、下周期生效的套餐变更。
4. AI API 用量事件接收、持久化、幂等、异步处理、聚合、迟到数据处置。
5. 使用确定性规则进行按量计费、套餐额度抵扣、月度出账和账单明细生成。
6. 后付费应收、简化复式记账、模拟渠道支付与退款、调整单与支付撤销。
7. 业务/账务/模拟支付渠道对账，失败重试、差异工单、人工核查路径。
8. Redis 热点数据缓存、RabbitMQ 异步任务、Outbox、Redisson 多实例任务协调。
9. API 文档、单元与集成测试、Apifox 场景自动化、JMeter 并发与容量测试。
10. 基本指标监控、Docker Compose 部署、Linux 虚拟机双应用实例演练、GitHub Actions CI/CD、备份恢复。
11. 简洁的管理控制台，用于演示产品、订阅、计量、账单、支付、对账与运营状态；开发时间安排在核心后端闭环后。

### 1.2 明确不在首版范围

真实资金渠道接入、真实税务发票、会计准则合规认证、多币种结算、复杂优惠券系统、跨区域容灾、真正跨主机高可用集群、完整 ERP、Kubernetes、全量分布式微服务。**不把模拟账务项目宣传为真实银行/支付生产系统。**

预付费余额/授信、复杂升降级即时按比例计费、税费、Kafka 大规模事件流、AI Agent、Dubbo、Netty、限流熔断/降级、灰度发布等安排在稳定交付后的扩展阶段，扩展前需补充需求与兼容性验证。

### 1.3 首版具体产品规则

- **第一期产品：** AI API SaaS，采用**后付费自然月账单 + CNY 单币种 + 模拟支付渠道**。
- **计量维度：** 租户、订阅、模型、计量项（如 Input Token、Output Token）、发生时间、来源事件 ID。首版以整数 Token 为用量单位，可针对不同计量项独立定价。
- **套餐规则：** 固定月费可选、周期赠送额度、超额阶梯单价。优先支持“下一个账期生效”的套餐变更，避免首版引入复杂的当期按日分摊。
- **账期：** 自然月；租户账期时区显式配置，默认 `Asia/Shanghai`；使用租户时区确定账期边界，数据库统一存 UTC 时间；采用 `[start, end)` 左闭右开。
- **时间口径：** `occurred_at`（真实业务发生）、`received_at`（服务接收）、`processed_at`（聚合完成）分开记录。跨账期/迟到事件按规定处理，不暗改已确认账单。
- **金额口径：** 数据库精确十进制（`DECIMAL`）或明确的最小货币单位整数；计算使用 `BigDecimal`，**禁止 `float/double` 参与金额运算**。舍入方法、精度和舍入阶段由计费规则版本固定，避免逐条四舍五入与汇总后四舍五入产生差异。
- **历史数据：** 正式账单、计价快照、已入账分录保持可追溯；纠错以补充/调整/支付撤销记录表达，不覆盖原始事实。

**缓存判断：** 首版**不引入 Caffeine**。本项目对租户授权、价格和资金数据的一致性要求较高；多实例本地缓存失效管理成本通常超过收益。只有 JMeter / 指标证明 Redis 读取成为明确瓶颈，且数据低频变更、允许界定时效时，再对不可变价格版本进行局部本地缓存。

**中间件数量控制：** 起步仅 `MySQL`；按业务进展增加 `RabbitMQ`、`Redis`；监控阶段加 `Prometheus`。Nginx 在部署阶段使用。JMeter 与 Apifox 在 Windows 本地使用；无需另起同类服务。

## 3. 总体架构与核心流程

### 3.1 架构策略

**初期采用单 Maven 工程 + 单 Spring Boot 进程 + 按业务边界划分的模块化单体。** 不提前加入 Spring Cloud、Nacos、Seata 或 Dubbo，仅因为未来会微服务化而拆分进程并无收益，反而会增加远程调用与跨服务事务负担。

模块通过明确的 `Facade` / 应用服务 / 领域事件交互，禁止跨模块直接写对方业务表。模块内部可按 `controller → application/service → domain → persistence` 组织；不强制照搬复杂 DDD 框架。

```text
Apifox / Vue 管理台 / 模拟 AI API 客户端
                  |
              HTTP / Nginx
                  |
             MeterBill API
        Spring Security + Tenant
                  |
  +------------------------------------+
  | identity   catalog   subscription  |
  | metering   rating    billing       |
  | ledger     payment   reconciliation|
  | messaging  operations              |
  +------------------------------------+
       |            |           |
     MySQL      RabbitMQ      Redis
   [事实来源]  [异步任务]    [缓存/协调]
```

Windows 开发使用 IDEA 直接运行 Java 服务，Docker Desktop 运行 MySQL/Redis/RabbitMQ 等；Linux VM 通过 Compose 启动应用、依赖和 Nginx。所有配置通过环境变量或配置文件管理，密码和 Token 不得提交到 Git。

### 3.2 端到端计量计费主链路

1. SaaS 企业管理员创建租户、套餐、价格版本与订阅；平台签发有作用域的 API Key。
2. AI API 模拟客户端上报事件，字段包含租户、来源、`event_id`、模型、计量项、整数用量、`occurred_at`。
3. API 执行身份与租户校验、数据校验和业务幂等校验；**同一个 MySQL 本地事务**写入用量事件和 Outbox，再返回“已可靠接收/待处理”（如 HTTP 202）。
4. Outbox Dispatcher 重试投递 RabbitMQ；发布方启用 publisher confirms，消费方业务事务提交成功后确认消息；不可路由、反复失败事件进入可追溯失败处理流程。
5. Metering Worker 幂等处理、聚合统计、记录处理游标/状态。重复投递不重复增加用量；同一 `event_id` 不同请求载荷视为冲突。
6. Rating 使用**事件适用的价格版本**和账期额度计算费用，保存费用明细、版本快照与计算审计信息；支持确定性重算校验。
7. Billing 根据订阅 + 周期生成唯一正式账单；正式出账前执行一致性检查，已结算账期的迟到事件通过调整单处理。
8. Ledger 以原子事务记录借贷平衡的账务分录；支付模拟通道完成收款，重复回调不重复记账。
9. Reconciliation 以账单、账务分录、渠道流水形成差异清单，支持自动复核与人工处理，并记录审计轨迹。

### 3.3 事务及最终一致性边界

- 同一业务数据库事务能完成的变化，优先本地事务；**跨 MySQL 与 RabbitMQ 不宣称存在原子事务**，以 Outbox 保证可靠投递和可恢复性。
- 消息交付语义按**至少一次**假设设计；通过唯一约束、状态判断和可重入处理取得业务结果上的幂等。不得依赖 MQ 的“只消费一次”口号。
- 与外部支付模拟服务的结果先记录本地意图和唯一请求标识，再以回调、主动查询、对账修复未知状态；超时不等于支付失败。
- 分布式锁只负责降低并发竞争，数据库约束和事务是最终正确性屏障；Watchdog 续期不保证极端停顿后旧持锁者绝不继续执行。

## 4. 不变量、安全与状态机（强制验收）

### 4.1 全局不变量

| ID | 不变量 | 主要证据 |
| --- | --- | --- |
| INV-01 | 相同 `(tenant_id, source_id, event_id)` 只产生一条被接受的计量事实；冲突载荷必须可识别 | 唯一键 + 重复/冲突用例 |
| INV-02 | 每条合法计量事实最多进入对应计费结果一次，重复 MQ 投递不增加费用 | 幂等记录 + 消费重放测试 |
| INV-03 | 相同订阅、账期和正式账单类型不会被重复正式出账 | DB 唯一约束 + 并发出账 |
| INV-04 | 正式账单的价格规则/计算明细有快照，后续改价不回写历史金额 | 版本变更回归 |
| INV-05 | 每笔已入账账务交易的借方金额合计等于贷方金额合计 | 事务约束 + 核对 SQL |
| INV-06 | 重复支付、退款回调不能形成重复收付或重复分录 | 唯一请求 ID + 幂等用例 |
| INV-07 | 退款累计额度不得超出合法可退金额；异常状态迁移不得成功 | 并发退款/状态机测试 |
| INV-08 | 任意租户无权访问其他租户的资产、账单和运营数据 | 两租户自动化越权用例 |
| INV-09 | 失败的消息/任务必须可定位、可重试、可核对，不允许无声丢失 | 故障演练与补偿记录 |
| INV-10 | 备份不仅能生成文件，还必须能够通过实际恢复测试 | 恢复演练报告 |

### 4.2 安全基线

- 管理用户使用 Spring Security 实现认证与 RBAC（角色权限）；API Key 按最小权限、有效期、启停/吊销设计，只保存安全哈希，明文仅签发时展示。
- 所有业务查询需带可信租户上下文；MyBatis-Plus 多租户拦截器仅是辅助防线，复杂 SQL、原生 SQL、批处理和管理权限接口需额外测试。
- 不信任客户端提供的 `tenant_id`、价格、费用和角色。金额由后端计算，所有高风险操作审计。
- 密钥、数据库口令等通过 `.env`（本地）或部署 Secret 注入；`.env`、备份及测试敏感数据不得提交仓库；日志脱敏。
- 外部 API 输入校验、速率/大小限制、统一错误码，重复幂等请求采用明确响应语义。
- 演示环境使用合成数据，不处理真实支付信息或个人隐私。

### 4.3 关键状态设计

- 订阅：`PENDING → ACTIVE → (CANCEL_SCHEDULED | EXPIRED | CANCELED)`；禁止从已终止状态无条件回到 ACTIVE。
- 用量：`RECEIVED → PROCESSING → PROCESSED`，失败进入 `RETRYABLE_FAILED / FINAL_FAILED`，支持可审计重试。
- 账单：`DRAFT → ISSUED → PARTIALLY_PAID / PAID`，按业务增加 `VOIDED / ADJUSTED`，不允许随意逆向编辑已出账账单。
- 支付：`CREATED → PENDING → SUCCEEDED / FAILED / UNKNOWN`；`UNKNOWN` 必须通过查询或对账收敛，不简单当作 FAILED。
- 退款：`REQUESTED → PENDING → SUCCEEDED / FAILED / UNKNOWN`，每次重试沿用相同退款幂等标识。
- 对账差异：`OPEN → INVESTIGATING → RESOLVED / WAIVED`；需记录原因、证据、操作人。

以上为第一版状态草案；各模块技术设计阶段必须补充合法迁移矩阵、并发更新条件、补偿动作、幂等键和失败场景。不可用通用 `updateStatus` 绕过状态机约束。

## 5. 数据库、索引与数据迁移规范

1. **Flyway 唯一管理正式 Schema 变更**，初始建表、唯一约束、索引、默认数据均记录在 `src/main/resources/db/migration/Vxxxx__description.sql`。脚本一经应用到持久环境不得直接修改，用新版本前向迁移。
2. 不采用运行时自动建表替代迁移。MyBatis-Plus Generator 用于 Entity、Mapper、XML 和必要 Service 模板，优先从已经迁移成功的表生成 Java 基础代码；不得用生成器重写手写复杂 SQL 或业务服务。
3. 数据表按真实访问模式设计：租户维度查询、账期筛选、价格版本查找、待处理事件扫描、消息待投递扫描、账务交易关联等。首先明确 SQL 和选择性，再建立合适的联合索引。通过 `EXPLAIN ANALYZE`、慢 SQL、实测确认收益。
4. **示例唯一约束（设计意图，非已实施 DDL）：** 用量事件 `(tenant_id, source_id, event_id)`；主账单 `(tenant_id, subscription_id, period_start, period_end, invoice_kind)`；账务交易 `business_type + business_id + posting_action`；支付/退款 `channel_id + external_request_id`。具体字段和空值策略在相应 M 模块确认。
5. **示例查询索引（最终需用查询验证）：** 用量 `(tenant_id, subscription_id, occurred_at)`；Outbox `(status, next_retry_at, id)`；账单 `(tenant_id, status, issued_at)`。避免无脑给每一列建索引及在大表上随意 `SELECT *`。
6. 账务数据采用不可变分录、可审计调整或支付撤销；业务数据使用明确的唯一键、必要的 FK/一致性校验，不允许简单的物理删除破坏引用关系。
7. 数据库时间统一按 UTC 存储，Java 时钟优先使用 `Instant`，账期本地时间由显式 `ZoneId` 推导；开发/部署时固定时区和连接参数。
8. 生成演示数据使用固定随机种子、固定基准时间和可重入的装载命令；性能数据生成与正式业务数据库隔离。
9. 数据版本发布采用兼容性优先的 Expand → Deploy → Contract 思路；数据库迁移和应用回退须分别规划，**镜像回滚不等于账务数据回滚**。

## 7. 编码效率与协作协议（强制）

### 7.1 每轮改动的唯一呈现格式

所有实际代码修改步骤严格使用：

> **修改文件 “完整相对路径/文件名” -- 修改内容：具体添加/替换什么 -- 本次修改作用：解决什么业务/技术问题**

若涉及多个文件，每个文件都按照该格式说明，顺序按**基础设施 → 数据迁移 → Entity/Mapper → Service → Controller → 测试**组织。完整代码放在对应文件说明下；禁止只说“在某个 Service 中加一段代码”而不给路径。没有修改的文件不重复列出。

每轮交付还应包含：先决条件、需执行的命令、Apifox 请求或测试步骤、预期结果、排查要点、完成判定。代码设计与执行结果严格区分；未在用户环境测试不能宣称已通过。

### 7.2 复用与生成规则

- 优先使用 Lombok 简化日志、构造方法和数据样板；业务边界仍明确，避免无约束暴露可变实体。
- MyBatis-Plus FastAutoGenerator 生成 Entity、Mapper、XML 及必要样板；禁止为展示架构而重复手写已有功能。
- 统一 REST 响应、全局异常、业务错误码、参数校验、分页、审计字段、租户上下文、Trace ID、时间与金额工具。
- DTO/VO 与数据库 Entity 分离；金额计算/账务分录/支付状态必须使用明确业务类型与校验，不抽象成万能 CRUD。
- Mapper 可用于简单查询，但跨模块写表应经过目标模块暴露的应用服务/接口；关键更新必须检查受影响行数、幂等和事务边界。
- 参数化配置而非硬编码；配置文件区分 `local`、`test`、`vm`，命令与容器镜像版本在 M00 固定。
- 一次可以批量给出多个文件代码，但**每轮应是完整、可编译、可验证的业务增量**。

### 7.3 Git 与版本管理

- 建议 `main` 保持可运行；按模块或独立任务提交有含义的 Commit；重要里程碑打 Tag。
- Flyway SQL、代码、测试、配置示例、文档一同进入 PR/Commit；测试失败的增量不标记完成。
- 禁止提交 `.env`、密钥、数据库数据卷、JUnit/JMeter 临时结果、大体积压测数据。
- 重大架构取舍建立 ADR：问题、选项、决策、理由、影响、复审条件。

## 9. 测试工具分工与 Apifox 深度学习路线

### 9.1 工具分工

| 工具 | 负责范围 | 不替代的内容 |
| --- | --- | --- |
| **Apifox** | API 设计/文档、Mock、环境、变量、链路场景、数据驱动回归、可用的 CLI/CI 集成 | 不替代内部事务和 DB 约束测试 |
| **JUnit + Mockito** | 金额、定价、状态机及纯业务规则单元测试 | 不替代真实 MySQL/MQ 的运行特性 |
| **Testcontainers** | MySQL、RabbitMQ、Redis 的真实集成测试、事务/消息重复处理 | 不替代完整 E2E 和大型压力测试 |
| **本地 JMeter** | 吞吐、P95/P99、容量、稳定性与竞争场景 | 不替代细粒度业务断言与账务核对 |
| **Actuator + Prometheus** | 请求、JVM、线程池、待投递消息、对账与任务等指标 | 不替代业务审计或日志追踪 |

### 9.2 分阶段深入使用 Apifox

- M00：创建 MeterBill 项目、`Local/VM` 环境、OpenAPI 导入或同步、鉴权模板、通用响应断言。
- M01–M03：测试变量、登录/API Key 获取、租户 A/B 的越权验证、链式业务创建、场景重置/清理。
- M04–M06：端到端场景（开通 → 用量 → 出账 → 支付 → 对账）、数据驱动边界测试、状态机非法转换、Mock 支付回调。
- M07–M08：重复回调、并发前置条件、环境隔离与回归套件；需要压测的场景迁移到 JMeter 专用计划。
- M10：核对当前 Apifox 账号对 CLI/CI 和报告功能的支持情况，将必要的场景回归接入 GitHub Actions，保存报告。

**文档单一事实来源：** 以后端生成的 OpenAPI 契约为基础，Apifox 负责用例、环境与 Mock；接口发生变更要维护同步规则，避免无意覆盖人工编排用例。

### 9.3 JMeter 基线标准

- 本地 GUI 用于编写和调试 `.jmx`；正式测试使用非 GUI 模式。至少区分：基础吞吐、阶梯加压、持续稳定性、并发出账冲突、重复计量上报。
- 保存测试机器（CPU/内存、Windows 与 Docker 资源配额）、数据规模、线程数、Ramp-up、持续时间、请求成功率、吞吐、P95/P99、错误类型和系统指标。
- 压测后**必须**以数据库 SQL 与账务不变量验证结果，不得只依据 JMeter 响应成功率。
- 首轮记录基线，后续优化需同场景对比；不预设虚构的“生产级 QPS”。

## 10. 可运维性、高并发与高可用的验证路线

### 10.1 必须处理的故障类型

- MySQL 事务失败或死锁：事务重试条件与幂等核验；绝不盲目无限重试。
- RabbitMQ 无法访问、发布确认失败、消费后未 ACK：Outbox 重投与消费者幂等；限制重试次数并可人工恢复。
- Redis 中断、锁续期失败、应用 STW/进程终止：关键业务退回 DB 不变量保护，锁失效不能造成重复出账。
- 模拟支付结果未知、回调重复/乱序、主动查询超时：稳定幂等标识、状态机与后续对账收敛。
- 跨账期迟到用量、重算、套餐价格变更：不可变历史、调整账单和审计。
- 单个应用实例退出、重新部署：无状态 API、可安全重试任务、Nginx 路由到存活实例。

### 10.2 监控（最小可用）

保留 `Actuator + Micrometer + Prometheus`。至少提供：应用健康、JVM、HTTP 错误与延迟、数据库连接池、Outbox 待投递量与最旧事件等待时间、MQ 消费失败/重试、账单出账失败率、计量积压量、对账差异数量。Grafana 如确实需要可视化再加；不在首版强制 ELK/Loki/Jaeger。

健康检查按 liveness/readiness 区分；外部依赖短暂异常是否影响 Readiness 要有明确策略。对监控端点进行网络隔离/访问控制。

### 10.3 高可用范围的准确表述

- M00–M09：本地单服务 + Docker 依赖，重点验证**故障恢复能力**和承载能力，不声称“已经高可用”。
- M10：Linux **单台虚拟机**上双实例 + Nginx，可验证应用进程层故障转移；MySQL、Redis、RabbitMQ 和宿主机仍是单点，不等于跨主机容灾。
- 后续若有第二台以上独立机器，再考虑数据库副本故障切换、MQ 集群、备份异地存储与流量入口高可用。

## 11. Docker、部署与 CI/CD 规范

### 11.1 Docker Desktop 本地开发

- 所有依赖组件由 Docker Desktop 拉取和运行；以 `compose.yaml` 管理 MySQL、Redis、RabbitMQ，按需启用 Prometheus。
- 开发期间 IDEA 中直接运行 Spring Boot；MySQL/Redis/RabbitMQ 容器要有固定镜像版本、持久化卷、健康检查、服务名与端口映射。
- 初始化前检查已有端口占用，必要时通过 `.env` 映射到不同宿主机端口；数据库密码不得明文提交。
- 以 `docker compose up -d`、`docker compose ps`、`docker compose logs` 为基础流程；具体参数、镜像 Tag 和目录在 M00 给出。

### 11.2 Linux 虚拟机部署

- 验收前记录 VM 发行版、CPU/内存/磁盘、Docker/Compose 版本及虚拟机网络；据此确定服务与监控资源限制。
- Docker 化应用并通过 Nginx 反代，配置 Health Check、容器重启、持久化卷、日志轮转和证书/网络策略。
- 部署保留可用的上一版镜像，发布前数据库备份；迁移脚本采用兼容性策略，不将业务账务数据随镜像回滚。
- 至少实践一次备份**恢复**与一次双实例进程故障演练，保留结果。

### 11.3 GitHub Actions 的质量门禁

```text
push / pull request
    ↓
Maven compile + static checks
    ↓
JUnit unit tests + Testcontainers integration tests
    ↓
Build Docker image + image checks
    ↓
Push version-tagged image to registry
    ↓
Deploy to VM staging target (authorized secrets)
    ↓
health/readiness + smoke/Apifox CLI (subject to plan/tool availability)
    ↓
archive reports + mark release
```

部署所需 SSH 密钥和镜像仓库凭据只放 GitHub Secrets 或等效安全存储；不为 CI 任意开放 VM 端口。若本地虚拟机无法安全地被 GitHub 托管 Runner 访问，优先使用经过限制的自托管 Runner 或拉取式发布，而非公网裸露 SSH。

## 13. ADR、变更控制与版本纪律

架构决策文档位于 `docs/adr/ADR-NNN-主题.md`，记录背景、可选方案、选定方案、依据、影响范围、重新评估条件。建议首批 ADR：

- ADR-001：为什么第一阶段采用模块化单体而不是 Spring Cloud 微服务。
- ADR-002：为什么核心阶段采用 RabbitMQ，而 Kafka 留给大型计量数据流扩展。
- ADR-003：Redis 单层缓存与不引入全局 Caffeine 的原因。
- ADR-004：为什么使用 Flyway、计价快照和不可变账务分录。
- ADR-005：分布式锁仅用于协调，DB 幂等/唯一约束作为最终保障。

**变更规则：** 如果业务需求证明当前架构不合适，可以修订方案；同时修改本规范、相关模块文档和测试计划，记录兼容性、数据迁移、回归范围与提交号。不要为了维护原计划而保留不正确设计。

## 14. 部署完成后的 DLC 扩展（不阻塞 V1.0）

| DLC | 方向 | 启动条件 |
| --- | --- | --- |
| DLC-01 | 限流、熔断、降级与过载保护 | JMeter/监控发现真实服务容量边界 |
| DLC-02 | 灰度发布与快速回滚 | VM 多实例部署流程稳定；具备版本化镜像与健康检查 |
| DLC-03 | Spring Cloud 微服务化 | 模块边界稳定；有必要独立扩缩计量与账务服务 |
| DLC-04 | Dubbo RPC | 微服务拆分后，验证对当前 Spring Boot/JDK 的实际兼容与收益 |
| DLC-05 | Netty 专用计量接入网关 | 明确的长连接/自定义协议/网络 I/O 瓶颈需求 |
| DLC-06 | Kafka 事件流 | 高吞吐、可重放多消费者事件流需求确立 |
| DLC-07 | 只读财务差异分析 Agent | 核心账务稳定，Agent 仅提供解释/建议；操作受审批与审计约束 |
| DLC-08 | 预付费、授信、优惠/税务、多币种 | 新业务规则与账务模型先完成独立设计评审 |

**DLC 不等于已经实施。** 引入任何 DLC 前先描述真实业务目标、性能与可靠性收益，以及新增运维成本。
